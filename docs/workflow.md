# 用文件组织工作

DUMMYSYS 解决的是 Agent 把文件散落在各处、换一次会话就要重新交接的问题。约定目录、记录归属和阅读入口，能让人先看当前结论，再按需查原始证据。

## 四种归属

| 内容 | 放在哪里 | 谁维护 |
|---|---|---|
| 可维护的源码、测试、构建声明 | 独立代码仓库 | Git 与该仓库的开发规则 |
| 项目背景、当前结论、普通笔记 | Vault 中所属项目或知识目录 | 人和 Agent 编辑正文 |
| Project/Task/Run 身份、状态、配对与关联 | Vault Properties 和 runtime 记录 | CLI/core 受管操作 |
| 执行输入、日志、结果、源码快照、本机配置 | runtime | 对应执行者或安装工具 |

runtime 中的 Run 证据、项目配对和恢复记录有长期价值。不能因名字里有 runtime，就把它当作缓存整体清空。

## 什么时候建立 Project、Task、Run

以“检查一批资料”为例：

- **Project**：持续主题，例如“资料质量检查”。它可以关联一个或多个代码仓库，也可以完全没有代码。
- **Task**：一个需要接续的工作，例如“核对本批数量与总和”。记录目标、范围、当前摘要和下一步。
- **Run**：一次实际执行，例如“首次统计”。写清来源、输入、执行动作、退出结果和证据；失败重试新建 Run，保留失败事实。

普通阅读、单篇笔记或参考资料，不必为每次动作建立 Task/Run。Task 用于持续执行、交接或需要验证证据的工作；目录本身不是任务。

同一仓库可以有多个 Task，一个 Task 可以跨多个会话和代码目录。工具的 CWD 只是本次操作位置；Project/Task/Run ID 才是工作记录的稳定身份。CLI 使用显式工作区或安装器生成的入口，不根据 CWD 猜测资料在哪里。

## 一次工作的闭环

1. 读工作区规则与所属项目 README，确认当前目标、资料归属和写入范围。
2. 创建或接续 Task；执行前登记 Run，真正开始时 start。
3. 源码写入仓库，结果和日志写入该 Run；结构字段使用 CLI 更新，普通分析正文直接编辑。
4. 执行结束后 finish，区分失败、完成与尚未验证；把当前结论和下一步写回 Task。
5. 运行对应检查，保留原始结果，给下一次接续一个明确入口。

创建 Run 只登记计划，不代表已经执行。完成 Run 不自动证明质量通过、Task 结束或已经发布。源码修改也不会自动升级已安装的工作台。

## 跨会话交接

交接时通常只需工作区位置、Task ID、当前目标以及本次允许操作的范围。接续者先查询：

```text
dmy --workspace <工作区绝对路径> context --task <Task-ID> --section reading --json
```

沿返回的阅读路由读当前正文；需要追溯时才查 Run。context 不会把资料自动注入模型，也不代替项目规则或用户授权。不要把全部历史日志塞进一次会话。

`--actor` 是操作的执行者标识，可由任意工具显式提供。现有实现仍有 Task owner 和 Run actor 检查；跨工具不代表可以冒用别人身份。需要交接负责者时使用 `task handoff`，先通过 capabilities 查看契约。

## 治理的边界

工作方式是“工作约定＋CLI 受管操作＋校验”。范围声明帮助审计和协作，不是操作系统权限隔离，工具不会拦截其他程序任意写文件。它也不分派 Agent、不管理 Agent 团队，不承担跨机器自动同步。

开始实际演练见 [入门示例](quickstart.md)。本项目随作者工作流演进；使用者自行维护部署、版本选择和数据备份。
