# 更新已安装的 DUMMYSYS

用户在本仓库要求「更新」时，从目标版本构建并更新本机已配置的工作区，随后核对运行结果。「更新源码」只同步 Git checkout。「查看更新步骤」只读。安装新工作区参照 [安装](../INSTALL.md)。

1. 确定目标。使用用户指定的工作区和 commit 或 tag。省略工作区时，使用本机配置中唯一明确绑定的现用工作区。省略版本时，获取配置的发布分支，默认 `origin/main`，并固定其提交 ID。保留当前工作树和本地修改，从目标提交建立干净的独立 worktree。首次使用本指南前已经安装且两套固定入口要指向同一个 wheel 发行。
2. 执行。切换期间暂停编辑及其他写入。使用工作区常用的 Python 版本，在该 worktree 运行以下命令。填写工作区的实际绝对路径。依赖已准备好时传 `--wheelhouse <绝对路径>`，现用原生窗口依赖自动保留，也可通过 `--desktop` 显式启用。当前原生窗口使用的快捷方式和设置继续沿用。

   ~~~text
   python -I -X utf8 -B dummysys-cli/scripts/update.py --workspace <工作区绝对路径>
   ~~~

   Windows 可用 `py -3.13` 替代 `python`，macOS 可用工作区对应的 `python3`。脚本构建三个包、核对独立环境及治理检查、备份控制文件并切换。它通过固定入口检查 CLI 和 Workbench，通过已认证的服务读取项目清单。更新前已经运行的服务会保留运行状态，原有窗口需要通过常用入口重新打开。数据目录和个性化配置保持原位。
3. 验收。以脚本退出码和 JSON 回执为准。确认 `commit` 与目标一致，并报告发行和已有治理问题数量。`already_current` 表示固定入口已绑定目标提交。证据、备份及 wheel 在实际 runtime 的 `state/cli/updates/<发行 ID>` 下。
4. 处理失败。构建失败保留日志，修复原因后重试。切换失败先读 `failure.json` 的 `rollback_verified`。出现 `state/workspace/update-pending.json` 时，按其指向的 `controls.json` 与编号备份核对四个控制文件；仅在确认无写入者、服务已退出且现有内容分别匹配对应的切换前或切换后快照时恢复旧文件及原权限。核对固定 CLI 和旧服务后再移走待处理标记。待恢复的治理 Operation 按原发行的治理恢复流程处理。涉及资料格式迁移时使用目标发行的迁移说明。
