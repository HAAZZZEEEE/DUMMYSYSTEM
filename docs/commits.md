# 语义提交与推送规范

本规范适用于本仓库后续提交，与开发所在操作系统无关。提交记录应让未参加开发的人看懂：改了什么、为什么改、影响哪里，以及验证到什么程度。根 AGENTS 将它作为默认执行要求，无需用户逐次提醒。

## 提交标题

统一格式为 `type(scope): 中文动作与结果`。有不兼容变化时使用 `type(scope)!: 中文动作与结果`，并在正文末尾写 `BREAKING CHANGE: 受影响契约及调用方需要采取的动作`。

- `type` 必须来自下表，`scope` 必填，均使用小写英文；冒号后保留一个空格。
- `scope` 表示稳定模块或责任范围，优先使用 `core`、`cli`、`workbench`、`install`、`governance`、`repo`；更小的范围可用连字符连接。不使用机器名、人员名、日期或私人任务编号。
- 中文摘要用明确动作说明对象与结果，尽量不超过 72 个字符，不以句号结尾。读者无需打开 diff 就能理解该提交的目的。
- 禁止只写 `update`、`fix bug`、`修改`、`优化代码`、`同步`、`完成任务` 等无法辨认实际变化的标题。不能用 `chore` 掩盖功能、修复或重构。

| type | 适用变化 |
|---|---|
| `feat` | 新增可观察的功能或能力 |
| `fix` | 修复错误行为 |
| `refactor` | 调整内部结构，保持对外行为 |
| `perf` | 有明确目标和验证依据的性能改进 |
| `test` | 只调整测试、夹具或测试覆盖 |
| `docs` | 只调整说明、规范、开发指令或文档 |
| `build` | 构建、打包、依赖或安装工具链 |
| `ci` | 自动化集成与交付配置 |
| `chore` | 不属于上述类型的仓库维护 |
| `revert` | 撤销既有提交；正文注明被撤销的提交和原因 |

类型按实际意图选择。例如修复安装器错误可以用 `fix(install)`，调整打包流程可以用 `build(install)`。修复附带的回归测试和说明与修复一起提交，不单独拆成 `test`、`docs` 提交。

合格标题示例：

```text
fix(workbench): 修复重复启动时未恢复已有窗口的问题
refactor(workbench): 将系统应用打开逻辑收敛到平台适配器
docs(workbench): 明确双平台默认开发与验证责任
docs(governance): 规范语义提交格式与推送流程
```

## 提交正文

标题之后空一行。正文至少交代改动动机、验证结果与影响边界；按复杂度展开，小改可以各用一句，避免复述文件清单。

- **动机与行为：** 哪种场景需要改变，改动后的行为或约束是什么；必要时说明选择的理由。
- **验证：** 实际执行了哪些相关检查以及结果；未执行的检查说明原因，不能把计划执行写成已经通过。
- **影响边界：** 说明兼容性、数据或部署影响。涉及双平台时分别说明 Windows/macOS 的影响与实测范围；纯文档改动可写明“仅文档检查，未执行原生平台回归”。

使用真实换行，不把字面量 `\n` 写进消息。通过 CLI 提交多段正文时使用消息文件或结构化参数，避免 shell 展开改写正文。不得写入私人 Task/Run 身份、会话标识、本机绝对路径、内网地址或凭据；这些信息留在外部工作记录。

## 提交范围与检查

1. 修改前检查分支、工作树和暂存区，识别自己的改动与并行工作。一个提交围绕一个可独立解释、审阅和回退的目的；相互依赖的实现、测试和说明放在同一提交中，独立目的分别提交。
2. 提交前逐项核对 `git diff`、`git diff --cached` 与未跟踪文件。按路径或差异块暂存，只提交已审阅内容；不使用全量暂存把其他任务夹带进来，也不清除他人改动以制造干净工作树。
3. 按改动影响完成相关验证。纯文档检查规则一致性、相对链接、差异和脱敏；行为、构建或安装变化执行对应回归。验证边界遵循 [开发规范](development.md)；格式正确不能替代语义清晰或功能验证。
4. 提交后检查最终标题、正文和文件范围，记录真实提交 ID。新写的合并、回退、压缩提交标题同样表达明确语义；合并正文说明来源与目的。历史提交不因新规范被批量改写。

## 推送与交付

1. 以用户当前授权为准。用户已要求推送时，完成必要检查后直接执行，无需再次索要相同许可；不要把“允许提交”自动扩大为发布或部署。
2. 核对远端 URL、仓库可见性、当前分支与目标分支，更新远端引用，检查本次将发送的完整提交集合，包括已有但尚未推送的祖先提交。分支未建立上游时默认推送到已配置远端的同名分支并建立跟踪，不擅自合并到主分支。
3. 使用显式远端和目标分支推送。遇到非快进先重新获取并核对差异；不默认强推、不删除远端分支、不改写已共享历史。发生冲突时保留双方变化，按当前任务范围处理。
4. 推送成功后查询远端分支提交 ID，与预期提交核对；若其他工作同时推进分支，核对本次提交是否已包含，并说明差异。不能只凭命令已执行就报告成功。
5. 交付给出提交 ID、语义标题、目标分支、验证结果和未验证范围。明确保留的无关工作、尚未合并到主分支或未部署状态，避免把推送等同于全平台验收。
